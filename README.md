# curtaincall

공연 예매처 백엔드. 판매 오픈 시각의 트래픽 몰림, 좌석 단위 경쟁, 결제 실패 보상을 MSA 구조에서 다룬다.

> 진행 중

## 기술 스택

| 구분 | 사용 |
|---|---|
| 언어·프레임워크 | Java 21, Spring Boot 3.5.16, Spring Cloud 2025.0.x |
| 빌드 | Gradle 8.14.7, 멀티모듈 |
| 저장소·메시징 | MySQL, Redis, Kafka |
| 프론트 | React, Vite, TypeScript |
| 실행 환경 | Docker Compose, GitHub Actions |

## 개발 환경

- JDK 21, `./gradlew build`로 전체 빌드(spotlessCheck, checkstyle, 테스트 포함). 포맷은 `./gradlew spotlessApply`로 맞춘다.
- IntelliJ: palantir-java-format 플러그인을 설치하고 Enable 해야 에디터 포맷이 spotless와 같아진다.
- 구조: `services/*`(서비스), `libs/*`(공통 모듈), `build-logic`(Gradle 컨벤션 플러그인).

## 실행

```bash
cp .env.example .env      # 기본값 그대로 쓸 수 있다
docker compose up -d --build --wait
```

- gateway만 `GATEWAY_HOST_PORT`(기본 8080)로 열린다. MySQL, Redis, Kafka, Mailpit은 개발 도구용으로 `.env`의 호스트 포트에 열려 있다(Mailpit 화면 8025).
- KOPIS, LLM 키 없이 뜬다(fixture, Mock 모드).
- 프로젝트를 나눠 동시에 띄우려면 `docker compose -p <이름>`과 함께 `.env`의 호스트 포트를 서로 다르게 바꾼다.
- 재시도를 넘겨 DLT로 간 메시지는 원인을 해소한 뒤 서비스의 관리 엔드포인트로 다시 넣는다(compose 내부망에서만 접근). `GET /actuator/dlt/{DLT 토픽}`으로 조회하고, `POST /actuator/dlt/{DLT 토픽}`에 `{"offsets":"0:3,1:0"}`(파티션:오프셋)을 보내면 그 메시지만, 본문 없이 보내면 DLT 전체를 원래 토픽으로 재발행한다. 소비 쪽 `processed_event`가 중복 처리를 막는다.
- DB 계정은 서비스마다 앱 계정(`<서비스>_app`, DML)과 Flyway 계정(`<서비스>_flyway`, DDL + DML)으로 나뉘고 둘 다 자기 스키마 권한만 갖는다. 권한은 `docker/verify-schema-isolation.sh [프로젝트 이름]`으로 확인한다. 계정이나 초기화 스크립트를 바꾸면 `docker compose down -v` 후 다시 기동해야 반영된다(초기화는 빈 볼륨에서만 실행된다).

## 기술적 의사결정

**예매처 시뮬레이션.** curtaincall은 기획사와 판매 대행 계약을 맺은 예매처라고 가정한다. 공연·공연장 정보는 KOPIS(공연예술통합전산망) 오픈 API에서 동기화하고, 원래 계약으로 받는 데이터(좌석 배치, 등급·가격, 회차, 판매 오픈 시각)는 객석 수 기준으로 생성한다. 좌석과 판매 데이터는 시연용 생성 데이터다.

**좌석 모델.** 좌석은 층·구역·열·번호·좌표를 갖고, 공연장 배치와 회차별 좌석 재고를 분리한다. 무대에 가까울수록 등급이 높아 앞열에 요청이 몰리는 실제 분포를 부하 테스트에서 재현할 수 있다.

**MSA, 모노레포.** gateway, user, event, queue, reservation, payment, notification, search-assist로 나누고 서비스별 DB 스키마를 쓴다. 대기열은 트래픽 특성과 확장 단위가, 검색 보조는 외부 의존·지연 특성이 달라 분리했다. 이 규모만 보면 모듈러 모놀리스가 더 맞는 선택이다. 그래도 서비스 간 일관성(Outbox, Saga)과 장애 격리를 직접 다뤄 보려고 MSA를 택했다. 분리 효과는 대기열 폴링, PG 지연, 부가 서비스 장애가 예매 API에 주는 영향을 측정해 확인한다. 한 PC에서 실행하므로 독립 배포·확장 효과는 측정하지 않는다. 저장소는 하나로 두고 Gradle 멀티모듈로 나눈다.

**Spring Boot 3.5에서 시작해 4.1로.** 현업에 가장 많이 깔린 3.x로 개발하고 메이저 버전업을 직접 진행한다. 3.5는 2026-06-30에 OSS 지원이 끝났고 Spring Initializr도 4.0 미만 생성을 막아, 4.1.2로 생성한 뒤 3.5.16과 Gradle 8.14.7(3.5 지원 범위)로 내렸다.

**좌석 점유는 MySQL 조건부 UPDATE.** 점유 방식 두 가지(조건부 UPDATE, `SELECT … FOR UPDATE` 비관적 락)를 같은 조건으로 비교했다. 앞열에 요청이 몰리는 분포(1만 석, 60초, 3회 중앙값)에서 둘 다 p95 4ms 안팎이고 교착과 락 대기 타임아웃은 0, 이중 점유도 없었다. 차이가 없어 추가 인프라 없는 조건부 UPDATE를 기본으로 쓴다(`curtaincall.hold.strategy`로 전환). 시나리오는 `perf/seat-hold`.

| 초당 요청 | 전략 | p50 / p95 / p99 (ms) | 성공 점유/초 | 교착·타임아웃 |
|---|---|---|---|---|
| 300 | 조건부 UPDATE | 2.2 / 3.7 / 6.7 | 65 | 0 |
| 300 | 비관적 락 | 1.8 / 3.6 / 6.9 | 64 | 0 |
| 1000 | 조건부 UPDATE | 1.9 / 3.5 / 5.4 | 90 | 0 |
| 1000 | 비관적 락 | 1.7 / 3.3 / 4.9 | 89 | 0 |

측정 조건은 reservation 인스턴스 하나, gateway 없이 서비스 직접 호출, 한 PC(16 CPU)에 MySQL·reservation·k6 동거, 재고가 금방 차서 응답 대부분이 409다. 초당 1000건에서 p95가 300ms를 넘는 실행이 있었고, 원인은 reservation의 DB 연결 풀(기본 10)이었다. 아래 판매 오픈 부하 절에 풀 크기별 결과를 적었다.

### 판매 오픈 1만 명 부하

오픈 시각에 1만 명이 진입해 대기열, 입장, 앞열 쏠림 점유, 주문, 결제 확정까지 한 사람씩 끝까지 가는 시나리오다(`perf/open-sale`, `run.sh flow`). 사용자마다 VU 하나이고, 점유가 충돌하면 좌석 상태를 다시 보고 최대 10번까지 다른 좌석을 고른다. 측정 조건은 한 PC(16 CPU, 29GB)에 전체 스택과 k6가 함께 있고, 서비스는 모두 인스턴스 하나다. gateway IP 한도는 해제하고 계정 한도(10/s, burst 20)는 기본값이다. 입장은 초당 50명, 동시 활성 300명(`admissionPerSecond`, `maxActiveUsers`).

| 항목 | 목표 | 결과 |
|---|---|---|
| 대기열 진입 p95 (1만 명, 분산 1초) | 200ms 이하, 에러율 1% 미만 | 325~533ms, 3회, 에러 0% |
| 같은 진입, 분산 2초 이상 | | 15ms (2초), 55ms (3초), 3.5~7ms (5초) |
| 좌석 점유 p95 | 300ms 이하 | 32~40ms (3회) |
| 초과 판매 | 0 | 0 (종료 후 확정 주문·좌석 재고 정합성 검사 4종 위반 0, 새로 띄운 스택에서 3회 재측정) |
| 결과 | | 1만 석 매진, 결제 확정 4617·4618·4669건(정합성 재측정 3회), 429·503 없음 |

매진 뒤에는 대기자에게 `SOLD_OUT`을 알려 주고(실행당 약 1만 5천 건), 3번 받으면 사용자가 대기를 포기해 실행이 약 220초에 끝난다. 정합성 재측정은 스택을 새로 띄운 직후(워밍업 없음)에 돌려 진입 p95 4.6~5.5초, 점유 p95 50~58ms였고 4분 40초 안팎에 끝났다. 3회차만 13분 53초 걸렸는데, 마지막 5~7석이 남았을 때 점유를 포기한 입장자 300명이 입장 슬롯을 토큰 만료(10분)까지 쥐고 있어 약 9분 늦게 끝났다. 입장 토큰은 회수할 수 없어 설계상 생기는 꼬리다. 1회차에는 PG 승인 Bulkhead 거절 4건과 같은 수의 FAILED 주문이 있었고 해당 좌석은 해제 뒤 다시 팔렸다. 이 꼬리의 개선안은 후속으로 검토한다. 진입 p95는 목표를 넘었다. 원인은 queue나 Redis가 아니라 한 PC의 gateway 한 대다. queue를 직접 호출하면 같은 1만 건에서 p95 66ms(연결 수립 단계에서 일부 실패는 있다), Redis는 CPU 7~29%에 명령당 15µs였고 queue의 503은 0건이었다. 같은 1만 건을 1초에 몰면 gateway CPU가 코어 8~9개 분량까지 올라 서비스를 막 띄운 첫 실행은 p95 4.1초, 워밍업 뒤에도 0.3~0.9초였다. 분산 시간을 2초로 늘리면 15ms로 내려온다. gateway를 늘리는 것은 한 PC 환경에서 측정하지 않았다.

#### 입장 상한은 50/300 유지

같은 시나리오에서 `admissionPerSecond`와 `maxActiveUsers`를 바꿔 점유 p95를 비교했다(좌석 상태 캐시 2초, DB 연결 풀 10일 때의 측정).

| 초당 입장 / 동시 활성 | 점유 p95 | 매진까지 |
|---|---|---|
| 50 / 300 | 43ms | 230초 |
| 100 / 500 | 141ms | 127초 |
| 100 / 1000 | 422ms | 107초 |
| 200 / 3000 | 2.0초 | 80초 |

이 PC에서는 동시 활성 1000명부터 점유 p95가 목표를 넘는다. 값은 환경에 따라 달라지므로 운영에서는 회차 등록 때 조정한다.

#### 대기열 폴링 부하는 예매 응답 시간에 영향이 없다

예매를 초당 50건으로 고정하고 대기열 폴링 9000명을 붙였을 때와 뗐을 때를 3번씩 비교했다. 점유 p95는 폴링이 없을 때 24.7~27.4ms, 있을 때 26.6~28.0ms였다. 폴링 자체는 p95 5~25ms(첫 실행 458ms).

#### 그 밖에 측정으로 바꾼 값

- 좌석 상태 캐시 TTL 2초 → 500ms. 충돌 수와 매진 시간이 줄고(매진 230→147초, 충돌 12051→10117), DB 조회는 초당 2회다. 캐시를 끄면 점유 p95가 오히려 올랐다(42.7→62.6ms). 권장 폴링 간격은 2초.
- 점유 요청이 초당 1000건일 때 reservation의 DB 연결 풀(기본 10)이 한계였다. 풀 10에서 처리량 660~740/s, p95 3초 이상. 풀 40에서 1000/s, p95 38~49ms(최종 3회, 처리 누락 0~25건). 락 대기는 원인이 아니었다(행 락 대기 150회 이하). 그래서 풀을 40으로 올렸다.
- 같은 IP의 폴링이 예매 요청을 밀어냈다. 한 IP에서 폴링 300명과 예매를 걸자 요청의 52%가 429였고 점유 54%, 주문 46%가 실패했다. 폴링 한도(IP 100/s, burst 200)를 따로 두자 점유·주문 실패가 0이 됐다(진입 직후 몇 초 429 137건, 그 사이 Retry-After로 재시도).
- payment Bulkhead(승인 20)는 PG 지연 1초에서 승인 시도의 6.8%를 빠르게 거절해 해당 주문을 실패 처리하고 좌석을 풀었다.

#### 남은 한계

- 좌석 배치도 캐시는 재시작 직후 동시 요청이 몰리면 요청 수만큼 DB를 읽는다(500동시, p95 1.4~2.1초, 오류 없음).
- 충돌(409)로 끝나는 요청도 1인 한도 행(`user_session_quota`)을 먼저 써서 커밋 fsync 비용을 낸다. 초당 1000건에서 요청의 약 90%가 이 경로다.

**AI는 예매 경로 밖에.** 자연어 검색어를 구조화된 검색 조건으로 바꾸는 데만 LLM을 쓴다. 대기열·좌석·결제에는 넣지 않는다. 출력은 서버에서 검증하고, 실패하거나 느리면 키워드 검색으로 fallback한다. API 키 없이 Mock 모드로 실행된다.

### 결제 Saga 수렴 검증

결제·환불 흐름에 장애를 넣고 모든 주문이 종결 상태로 수렴하는지, 종료 뒤 정합성 쿼리(13개 검사)에 위반이 없는지 확인한다(`perf/saga-convergence/run.sh`). 시나리오마다 DB를 비우고 payment를 새로 띄운 뒤 주문 20건으로 3회씩 돌렸다. 13개 시나리오 39회가 모두 통과했고, 종료 상태에 위반은 0건이다. 한 PC(16 CPU, 29GB)에서 다른 테스트가 함께 돌고 있었다.

| 시나리오 | 주입한 장애 | 기대 | 수렴 시간 |
|---|---|---|---|
| baseline | 없음 | 20건 확정 | 2초 |
| payment-restart / reservation-restart | 승인 처리 중 SIGKILL 뒤 재시작 | 20건 확정 | 51~53초 / 0~46초 |
| kafka-outage-before / mid | 브로커 중단 20초 | 20건 확정 | 4~5초 |
| pg-drop-response | 승인 처리 뒤 응답 유실 100% | 거래 조회로 20건 확정 | 5초 |
| pg-inquiry-down | 응답 유실 뒤 거래 조회까지 PG 중단 50초 | 조회 실패를 겪은 주문(10~14건)을 포함해 20건 확정, 이중 승인 0 | 16~22초 |
| pg-timeout | 승인 요청 무응답 | 조회 소진 뒤 망취소, 20건 실패 | 165~524초 |
| seat-loss | 승인 지연 중 점유 만료, 다른 사용자가 좌석 점유 | 10건 확정, 10건 환불, 타 사용자 점유 유지 | 5초 |
| user-cancel-pg-down | 환불 중 PG 중단 | PG 복구 전 좌석 유지, 복구 뒤 환불과 좌석 해제, 환불 명령 1회 | 16~17초 |
| duplicates-reorder | 응답 중복, 순서 뒤바뀜, 명령 재전송 | 재생 전후 상태 동일 | 즉시 |
| dlt-replay | 소비 실패로 DLT 적재(reservation 테이블 일시 제거), 복구 뒤 관리 엔드포인트로 재투입 | 20건 확정, 승인 명령 재전송 0 | 재투입 뒤 7초 |
| pg-outage-breaker | 응답 유실 20건으로 서킷 열림 | 열림 중 10건은 PG 호출 없이 실패하고 좌석 해제, 닫힌 뒤 신규 주문 확정 | 열림 10초 |

응답 유실도 서킷 실패율에 들어가므로, 유실이 몰리면 이후 승인은 PG를 호출하지 않고 안전하게 실패한다. 서킷 상태는 payment 프로세스 메모리에 있어 시나리오마다 payment를 새로 띄운다.

판정 기준과 측정 한계는 다음과 같다. pg-inquiry-down은 조회 실패를 겪은 주문이 1건 이상인지로 주입이 걸렸는지만 보고, 수렴과 PG 이중 승인 0건은 공통 검사에서 판정한다. 정지 전에 조회를 끝내는 주문이 구조상 생기므로 20건 전부를 요구하지 않았고, 겪은 주문 수는 3회 각각 10/14/10건(20건 중)이었다. PG 취소는 이중 환불이 없음(적용 1회)만 확인했고, 재전송을 흡수한 취소(`applied=false`)는 한 번도 측정되지 않았다. dlt-replay의 `replayed`는 DLT 토픽이 회차 사이에 누적되어 이전 회차 메시지까지 포함한 값이며, 소비 쪽 멱등 처리 덕에 결과에는 영향이 없다.

## 작업 방식

이슈는 epic(서비스·기능군) > story(기능 ID 또는 사용자 화면 단위 요구사항, 수용 기준 포함) / task(환경·성능·검증) / bug로 나누고, epic 아래에 하위 이슈로 연결한다. 이슈에는 유형과 서비스 라벨만 붙이고, 변경의 성격(type)은 PR 제목과 PR 라벨로 정한다. story 하나가 브랜치 `<type>/<이슈번호>-<설명>`과 PR 하나에 대응한다. 이슈 브랜치는 `dev`에서 나와 `dev`로 squash merge한다. 마일스톤이 끝나면 `dev`를 `main`에 merge commit으로 올리고 태그를 붙인다. `main`은 항상 릴리스 가능한 상태다. PR 제목은 Conventional Commits를 따른다. 커밋 템플릿은 `git config commit.template .gitmessage.txt`로 쓴다.

| 이슈 유형 | 주로 쓰는 PR type |
|---|---|
| story | feat |
| task | build, ci, perf, test, refactor, chore, docs (새 기능을 추가하는 작업은 feat) |
| bug | fix |
